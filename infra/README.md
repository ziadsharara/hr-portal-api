# infra/ — read this before running `terraform apply` anywhere

This Terraform module provisions **one shared AWS stack** for both
services. It is a single stack, not two, because the frontend's S3
bucket policy and the backend's security group are governed by the same
`api_allowed_cidrs` variable, and the frontend's deploy role has to be
granted access to a bucket the backend's stack owns.

## Only ever run `terraform apply` from ONE copy

Because `hr-portal-api` and `hr-portal-frontend` are separate git repos,
an **identical copy of this `infra/` directory exists in both** (a
deliberate simplicity tradeoff over a dedicated third infra repo). That
duplication creates one real risk:

> Applying from both copies would try to create the same EC2 instance,
> S3 bucket, ECR repo and IAM roles twice — either a hard failure on
> name collisions, or, worse, two divergent state files each believing
> they own the same real resources and fighting on every future apply.

**Canonical copy: `hr-portal-api/infra/`.** That is the one anyone should
apply from. `hr-portal-frontend/infra/` is a synced read-only mirror kept
for visibility in that repo's PRs, and is never applied from.

If you change anything under `infra/`, change it in the backend repo
first, then copy the change into the frontend repo so the two do not
drift. Note that `infra/user_data.sh.tftpl` reads
`../db/init/01_schema.sql`, which exists only in the backend repo — the
frontend mirror carries a copy purely so `terraform validate` can run
there.

## What this provisions

    Browser
      |
      +--> S3 website endpoint ............ the Vue bundle (static files)
      |
      +--> EC2 public IP (Elastic IP) :8080
                |
                +-- backend container ..... Spring Boot, published port
                +-- mysql container ....... NO published port, ever
                       |
                       +-- /var/lib/hr-portal/mysql -> dedicated EBS volume

- **S3** (`s3.tf`) — static website hosting for the Vue build, with
  `error_document = index.html` so Vue Router's history mode survives a
  hard refresh. Versioned, so a bad `sync --delete` is recoverable.
- **EC2** (`ec2.tf`) — one instance, Amazon Linux 2023, running both
  containers via Docker Compose. Bootstrapped by `user_data.sh.tftpl`.
- **EBS** (`ec2.tf`) — a dedicated volume for MySQL's data directory,
  carrying `prevent_destroy`, so replacing the instance does not destroy
  the database.
- **ECR** (`ecr.tf`) — the backend image only. The frontend no longer
  builds a container.
- **Secrets Manager** (`secrets.tf`) — MySQL credentials, generated by
  Terraform and read by the instance at boot. Never in tfvars or user
  data.
- **IAM** (`iam_ec2.tf`, `iam_github_oidc.tf`) — an instance profile
  scoped to pull-only ECR plus exactly one secret, and two GitHub OIDC
  deploy roles with no overlap.

## What is deliberately NOT here

- **No ALB, no ECS, no RDS.** This replaced an ECS Fargate stack; see
  `DEPLOYMENT.md` for what that migration gave up.
- **No TLS anywhere.** S3 website endpoints are HTTP-only and there is no
  certificate on the EC2 listener. Everything crosses the network in
  plaintext. This is the direct cost of having no domain and no CDN yet.
- **No remote state.** State is a local `terraform.tfstate`, which is
  fine for one person and unsafe for two. See `versions.tf`.
- **No automated database backup.** RDS's 7-day retention and
  point-in-time recovery went away with RDS. Nothing snapshots the EBS
  volume today.

The first three are acceptable for a development/demo environment. The
last one is the one that bites hardest if ignored — see `DEPLOYMENT.md`.
